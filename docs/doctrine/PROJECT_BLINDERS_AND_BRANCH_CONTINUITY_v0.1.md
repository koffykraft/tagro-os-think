# TAGRO OS Project Blinders & Branch Continuity Doctrine v0.1

Status: WORKING
Origin: OWNER + AI structured formulation
Scope: All TAGRO OS projects and AI-assisted builds

## 1. Purpose

TAGRO OS projects must resist conversational drift, enthusiasm drift, tool-driven drift, and AI accommodation drift.

A project begins with a bounded objective, approved assumptions, declared interfaces and a known design intent. Conversation may explore alternatives, but conversation is not authority.

## 2. Project blinders

Every project must have strict blinders, like a working horse:

- the project objective is explicit;
- the current scope is explicit;
- excluded work is explicit;
- governing doctrine and accepted design decisions are explicit;
- changes are not silently absorbed because they arose in conversation;
- AI may not remove, widen or reinterpret the blinders by itself.

## 3. Conversation is not guidance

Conversation is an exploration surface. It can generate questions, ideas, hypotheses, alternatives and candidate improvements.

None of those automatically changes the project.

A conversational idea may become project guidance only when it is deliberately promoted through an accepted change decision.

## 4. Change creates a junction

Any material change to the initial design must be considered, recorded and signed off.

Once accepted, that change creates a new project junction. It may be a continuation in business purpose, but architecturally it becomes a new project state with its own lineage.

The previous project state remains addressable.

## 5. Divergence is preserved

Branches are not merely temporary code paths. They represent alternative project realities.

A branch that is abandoned, deleted from active development, or superseded must remain recoverable through Git history, tags, commits, records or archive references.

TAGRO OS should be able to:

- return to a previous junction;
- revive an abandoned direction;
- extract one successful idea from a failed branch;
- dock that idea into an earlier or later junction;
- retain the abandoned structure in limbo without treating it as active doctrine.

## 6. No silent branch inheritance

A successful component from one branch does not authorize the rest of that branch.

Components, ideas and techniques must be individually promotable.

The receiving project must evaluate the imported component against its own doctrine, dependencies, shadows and contracts.

## 7. Primer principle

AI output, early layouts, schemas, page structures, component placements, calculations, styles and implementation choices are primer coats and pencil lines unless explicitly accepted.

They are working material, not permanent truth.

Do not over-engineer a provisional element that is expected to be overpainted, replaced or deleted.

The required finish should match the maturity of the decision:

- SEED — sketch only
- WORKING — enough to test the idea
- REVIEW — enough to compare and verify
- ACCEPTED — sufficiently engineered for committed use
- INSTALLED / PRODUCTION — hardened, tested and maintained

## 8. Tomorrow must not dictate today's finish

Do not solve hypothetical future detail prematurely.

Build enough structure today to keep tomorrow replaceable.

Do not polish a primer layer as if it were the final painting.

## 9. AI obligations

An AI working on a TAGRO OS project must:

1. Read the current project contract and governing doctrine before acting.
2. Keep the stated objective and scope visible in its reasoning process.
3. Treat new conversational ideas as candidates, not directives.
4. Flag material divergence instead of silently implementing it.
5. Request or record explicit acceptance before changing project direction.
6. Preserve previous junctions and lineage.
7. Avoid over-finishing provisional structures.
8. Separate reusable ideas from the branch that produced them.
9. Record shadows when divergence or over-engineering causes failure.
10. Never interpret user enthusiasm about one component as authority to reshape the entire project.

## 10. Project state chain

PROJECT INTENT -> BLINDED SCOPE -> WORKING BRANCH -> EVENT / IDEA -> CHANGE CANDIDATE -> ACCEPT / REJECT -> NEW JUNCTION IF ACCEPTED -> CONTINUE

Rejected or superseded states remain traceable.

## 11. Core rule

Explore freely. Change deliberately. Preserve lineage. Finish only to the maturity required.
